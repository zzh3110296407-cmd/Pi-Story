## 原因与修复边界

已冻结的两次OPEN和一次CHAP共有36次无效调用：20次原始JSON多一个末尾右括号、8次圣经键格式错误、4次重复提交已建立的圣经、4次引文不匹配。20次语法错误的HTTP原始参数与SDK拒绝的参数一致，不能归因于适配层拼接，也不能通过删除括号后重算旧成绩。

- [错误回执](../../story/packages/pi-story/src/entries.ts)原先只在本地`details.error.items`保存字段路径，发给主笔的`content`却不包含路径。现在文本同时给出错误码、字段和建议；真实SDK替身验证主笔下一次请求能获得`items[0].quotes[0]`并提交正确引文。
- [SDK错误分类](../../story/packages/pi-story/src/index.ts)现在显式识别`ToolCall.argumentsError`。即使工具参数全部可选、解析失败后`arguments={}`恰好符合schema，也归为`DOMAIN_INVALID`，不再误报传输错误。反馈保留解析诊断，去掉整段`Received arguments`回显；原调用仍拒绝执行，不静默修剪JSON，不触发写手或提交。
- [参数契约](../../story/packages/pi-story/src/tools.ts)发布与既有core规则一致的圣经键pattern、种类与前缀对应、关系方向、逐字引文要求及大纲JSON闭合方式。重复提交初始圣经时，P2回执指向已启用的`read_story`和后续步骤，不再建议当前阶段无法执行的补充操作。合法参数和开书只提交一次的约束保持一致，core验证与上游源码未改。

本轮没有修改四份角色规则、模型、采样参数、验收阈值或评分器。工具描述及错误反馈属于本次作者要求的验收后契约修复，不能套用旧冻结运行证明新版本已经达到T01门槛。
