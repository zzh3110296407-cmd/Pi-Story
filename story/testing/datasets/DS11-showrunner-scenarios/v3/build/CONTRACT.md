## Format and action boundary

DS11 v3 uses story/p3-scenario@2. Its execution has internalRoles:faux, stopAt:decisive_action, maxReadOnlyCalls:3, maxShowrunnerRequests:6, maxChapterAttempts:2 and onBoundExceeded:record_failure_and_stop. stopAfterFirstAction is absent. The development-safe scenario-contract.mjs exports validateScenario, scenarioV1Schema, scenarioV2Schema and readOnlyTools. It performs static format checks, not the execution or scoring of decisions. The execution session adopts @2 at the existing datasets.ts boundary and implements plan30 S5 in its runner. The previous loader accepts only @1 and must not be used to claim @2 readiness.

A decisive action is the first non-read-only tool call in native emitted order, or a reply in a message with no tool calls. read_story, read_chapter, read_state and get_character are preparatory reads. Thinking text and preambles accompanying tool calls are not replies. A read-only turn does not end the measurement. In a parallel batch preserve emitted order; use the first non-read-only call, never select a later preferable mutation. Keep all emitted actions/results for forbidden-action and T04 audits. More than three reads before a decision, or six showrunner requests without a decision, is an observed failure, not missing evidence or NA. A read after a decisive action cannot change which action was decisive. Reply classes must give a substantive, correct answer; reads alone do not pass.

Existing DS11 programChecks strings remain verbatim per31 §2.1. In @2 their historical phrases 'first action' and 'next action' refer to the decisive action. A legacy stop constraint such as 'No further tool call' means no forbidden continuation after the stop/report; permitted preparation reads remain subject to the read bound, request bound and T04 relevance checks. This is versioned semantics, not a rewrite of archived @1 results. F categories now require a reply, with answer points in judgeChecks. DS14 v2 uses @1 and its E2E execution continues as before; its fifteen acceptance files and acceptance/index.json are byte-identical to v1.

## Parameter and semantic checks

argsMatch is primitive equality on dot/index paths. Constrain only determinable inputs: chapter number, an input-visible existing key when that representation is uniquely required, author-given source, and an operation uniquely determined by the request. Do not force newly invented keys, namespaces, attribute names, prose or a choice between equally reasonable classifications. A source:user, op:set update can augment an existing card or create a new rule; both representations are permitted when they preserve the complete user restriction, provenance, nonempty reason, author quote and future-only effect. The two forms are alternatives, not two updates that must both be made. referenceAction is only a core-valid witness, never an exact answer template. judgeChecks check the requested change, including any removed textual/field matcher. Existing setup, forbidden and program conditions still apply.
